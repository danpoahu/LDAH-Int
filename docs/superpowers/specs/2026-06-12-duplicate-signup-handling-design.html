Duplicate Signup Handling — Design

Date: 2026-06-12  ·  Status: Approved (design)  ·  Repos: LDAH-Int (Part 1), LDAH_W2 + App (Part 2)

Problem

Families occasionally sign up for the same event/date more than once (Lauren Vigil had two confirmed records for the June 17 Parent Talk Cafe, each firing its own confirmation email). Nobody — family or staff — usually notices until someone spots the same name twice. Staff have no clean way to remove the extra without the Cancel & Reschedule modal emailing the family, who don't even know they were in twice. This has happened before and will again.

Goal: (1) help staff catch and silently remove duplicates, and (2) warn people at the public form before they create one. Prevention is best-effort; staff-side removal is the real backstop.

Canonical duplicate definition

Same person + same event + at least one overlapping ACTIVE date.

  • Same person = same email (case-insensitive), linkedContactId as secondary match.
  • Overlapping active date = a date appears in two records' active dates. A date is active if not cancelled (dateStatusOverrides[date]==='cancelled' or doc status==='cancelled' excluded).
  • NOT duplicates: one signup choosing several dates (["June 10","June 24"]); two signups for different dates; same person across different events.

Shared by Part 1 & Part 2 so they never disagree — implemented once as a pure helper (findDuplicateDateOverlap() / datesOverlap()).

Part 1 — LDAH-Int: detect & silently remove ships first

Detection (client-side)

In the event's signup list / Event Attendance view, group the already-loaded signups by person and apply the definition. No backend, no new function, no triggers. Records in an overlap get a "Duplicate" badge.

Resolve action

Clicking the badge opens a modal showing the involved records side by side with the recommended keeper pre-selected:

  • Keep the record with attendance or feedback; else the earliest signup.
  • Warn if the record proposed for removal holds unique data the keeper lacks — so staff never silently lose history.

Staff confirm; staff may override which is removed.

Removal mechanism

  • Hard-delete the chosen doc from events/{eventId}/signups/{signupId} — the only guaranteed-silent path (there is onEventSignupCreated and onEventSignupUpdated with five email handlers, but no delete trigger, so a delete fires nothing).
  • Write an Audit Log entry (performedBy = current user): "Removed duplicate signup — Lauren Vigil / lmays8933@… — June 17 Parent Talk Cafe — kept Tzfd…, removed zWnC…" — a permanent record even though the doc is gone.
  • Recompute that event's signupCount/pendingCount from remaining signups (currently stale, e.g. 9/9 vs 3 real).

Permissions

superAdmin + admin (same gate as the Audit Log).

Part 2 — Prevention at the public form ships second

Where

Both signup implementations (they drift): W2 (events.html, vanilla JS) and the App (React). Same check in both.

When / behavior — warn but allow

Once email + dates are entered, check the email against existing active signups for that same event and compute date overlap. On overlap, show:

"It looks like you're already signed up for June 17. You can still submit if you meant to."

Lists only the overlapping date(s). They can proceed anyway; new dates unaffected. No hard block, no silent drop.

By design: the form only knows the typed email, so prevention catches same-person re-submits but not someone using a different email — which is why Part 1 exists.

Edge cases

  • Multi-date: one signup with several dates is one signup; only cross-record overlap counts; cancelled dates excluded.
  • Recurring events: recurringEvents/{eventId}/signups/…; same helper, same silent delete.
  • 3+ copies: modal handles N — keep one, remove the rest.
  • Different-email duplicate: not auto-detected (acceptable); staff can still remove manually by name.
  • Removed copy had attendance/feedback: warned before confirm. (Future: merge history onto keeper — out of scope.)

Out of scope (v1)

  • Backend scheduled scan + global dashboard "duplicates to review" roll-up (possible later).
  • Auto-merging attendance/feedback from removed copy onto keeper.
  • Hard-block / silent de-dupe at the form.

Testing

  • Unit-test datesOverlap/findDuplicateDateOverlap: identical → flag; disjoint → no flag; partial → flag; cancelled excluded.
  • Manual on STAGE: 2-record same-date dup → badge → modal recommends correct keeper → confirm → doc deleted, no email (verify Email Log), audit written, counts fixed.
  • Prevention on STAGE: email already registered for a date → warning for that date only; submit-anyway works; brand-new date → no warning.
